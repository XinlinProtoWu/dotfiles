foggy-llama
provides a command-line client, a model server, and handlers for health checks, model discovery, and chat
completions. The client sends HTTP requests over FoggyTCP v2. The chat handler streams server-sent events (SSE) using your
CP3 chunked response writer.
foggy-llama

When running a real model, the server uses llama.cpp, a C/C++ library that runs language models locally from GGUF files.
llama.cpp repository

2. Extend the HTTP server
Route lookup
Update foggy_http_server_listen() in foggy-http/src/foggy_http.cc . After parsing the request and initializing the
response, match the request method to the registered method and the full request target to the registered path. Both
comparisons must be exact and case-sensitive. For example, GET /health?x=1 returns HTTP 404 because the registered path
is /health .
A path can have both GET and POST handlers. Call the matching handler with the original request, the initialized response, and
its registered context. Keep the CP3 public HTTP headers and function signatures.

Routing errors
Implement two routing errors in foggy_http_server_listen() .
– Return HTTP 404 when the full request target has no exact match among the registered paths.
– For a matching path, handle OPTIONS as described below. Return HTTP 405 with an Allow header for any other
unsupported method.
For both errors, set Content-Type: application/json and send a JSON object with an error field. The field can contain any
valid JSON value. A short message string is enough, and you can choose its wording.

Fill the initialized foggy_http_response_t and pass it to the CP3 code in foggy_http_server_listen() that serializes and
sends a successful handler response. If you put that code in a helper such as write_response() , reuse that helper so the
response is framed correctly on a persistent connection.
The supplied model handlers generate their own application error responses.

OPTIONS requests
For OPTIONS on a registered path, return HTTP 200 with an empty body and an Allow header directly from the HTTP server.
Use Content-Length: 0 to delimit the empty response on a persistent HTTP/1.1 connection. You can omit Content-Type for
this response. For OPTIONS on an unknown path, return the same JSON 404 as for other methods.
For both HTTP 200 responses to OPTIONS and HTTP 405 responses, list GET and POST if registered, in that order, then
append OPTIONS . The possible Allow values are GET, OPTIONS , POST, OPTIONS , and GET, POST, OPTIONS . For example,
OPTIONS /health returns Allow: GET, OPTIONS .

Build and test
Run with the mock engine
From the project root, build the client and server with make cp4 . The first build initializes the submodules, including the new
thirdparty/llama.cpp submodule, prepares the pinned library, and downloads the course GGUF model (about 105 MB).
On Ubuntu arm64, Make compiles the llama.cpp CPU backend from source to support the course Ubuntu 22.04 VMs. Allow a
few minutes for the first build, depending on your VM and download speed. Subsequent builds reuse the compiled library.
Use --mock to test your routes and streaming responses with the deterministic backend.
make cp4
./build/foggy-server --mock

In another terminal, try the three routes.

Run the local checks
After completing both tasks and running make cp4 , run the test script from the project root.
python3 foggy-llama/tests/smoke.py

The script starts its own --mock server on 127.0.0.1 , selects an available UDP port, and stops the server when the checks
finish. It checks the three model routes, JSON routing errors, and OPTIONS responses with Allow .

Run with a real model
Start the server on UDP port 8084 with the course model prepared by make cp4 .
./build/foggy-server --model foggy-llama/models/SmolLM2-135M-Instruct-Q4_K_M.gguf --port 8084

In another terminal, send a prompt to the real model.
./build/foggy-client --port 8084 chat --prompt 'Say hello.'
