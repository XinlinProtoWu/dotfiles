# 10 — IP and DNS

> Source: `10-IP.pdf`. Goal: why connecting heterogeneous networks needs one common addressing scheme, and how DNS scales naming from a single `hosts` file to a global hierarchy.
>
> **Deck scope:** this lecture frames the Cerf–Kahn internetworking problems, then focuses on **DNS**. IP addressing, CIDR, NAT, and interdomain routing continue in [[11_BGP]].

## 1. The internetworking problem

In the 1970s, universities and labs each had their own local network. The goal became: **connect all of them**.

Cerf and Kahn (1974) listed the incompatibilities:

| Problem                                                       | Why it is hard                                                                    |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **(1) Different addressing**                                  | One network uses `44432`, another uses `3fab-0268`; neither understands the other |
| **(2) Different maximum data size**                           | A 2000 B packet may hit a network whose maximum is 1500 B                         |
| **(4) Unrecoverable mutation or missing data**                | Some networks drop or corrupt packets; delivery is not guaranteed                 |
| **(5) Different status, routing, fault detection, isolation** | Each network reports and handles failures differently                             |

![[10-IP.pdf#page=26]]
*Figure: connecting HKUST, HKU, AT&T, Airtel, and China Telecom — many separate networks. (`10-IP.pdf` p. 26)*

![[10-IP.pdf#page=27]]
*Figure: the four Cerf–Kahn challenges. (`10-IP.pdf` p. 27)*

**Core idea:** give every host a single **Internet address**, and define one common network-layer protocol — **IP** — that every network agrees to carry.

> [!example] No common address
>
> HKUST host says: *“My address is 44432.”*
> HKU host says: *“My address is 3fab-0268.”*
>
> Without a shared address format, neither host can even name the other. IP gives both a 32-bit IPv4 address (or 128-bit IPv6 address).

## 2. Names vs. addresses

Three identifiers are involved in reaching an application:

| Identifier | Answers | Example |
|---|---|---|
| **Domain name** | Which host, in human terms? | `www.ece.ust.hk` |
| **IP address** | Which host on the Internet? | `143.89.13.184` |
| **Port** | Which process on that host? | `443` for HTTPS |

![[10-IP.pdf#page=33]]
*Figure: a host name identifies the server; a port identifies the application/process. (`10-IP.pdf` p. 33)*

- **IPv4:** 32-bit number written as four dotted octets, e.g. `128.2.42.10`.
- **IPv6:** 128-bit number written as eight groups of four hex digits, e.g. `2001:0db8:...:7334`.

![[10-IP.pdf#page=30]]
*Figure: IPv4 and IPv6 address formats. (`10-IP.pdf` p. 30)*

> [!example] Why names exist
>
> Nobody wants to send email to `zilim@143.89.13.184`, and nobody wants to remember `143.89.13.184` instead of `ust.hk`. Domain names provide a human-memorable layer on top of IP addresses.

## 3. DNS design goals

The early Internet used **one central `hosts` file** managed by SRI. Every server periodically downloaded the latest copy. Your computer still has one: `/etc/hosts` on Linux, `C:\Windows\System32\drivers\etc\hosts` on Windows.

That approach cannot scale: too many names, updates, users creating names, and users looking them up.

DNS therefore aims to be:

| Goal                 | Meaning                                      |
| -------------------- | -------------------------------------------- |
| **Scalable**         | Many names, updates, users, lookups          |
| **Highly available** | The naming system should keep working        |
| **Correct**          | Globally unique names; consistent answers    |
| **Fast**             | Lookups should not dominate connection setup |

![[10-IP.pdf#page=38]]
*Figure: the old central `hosts` file does not scale. (`10-IP.pdf` p. 38)*

## 4. Three intertwined hierarchies

DNS scales by distributing along three dimensions at once:

1. **Hierarchical namespace** — names form a tree, not a flat list.
2. **Hierarchically administered** — different organizations manage different parts.
3. **Hierarchy of servers** — no single server stores every mapping.

![[10-IP.pdf#page=40]]
*Figure: the three hierarchies of DNS. (`10-IP.pdf` p. 40)*

### 4.1 Namespace hierarchy

A domain name is read right-to-left from the root downward:

```text
root
 |
 hk
 |
 ust
 |
 ece
 |
www
```

- `.hk` is a **top-level domain (TLD)**.
- `ust.hk` is a domain registered under `.hk`.
- `ece.ust.hk` is a subdomain created by HKUST.
- `www.ece.ust.hk` identifies the web server inside ECE.

![[10-IP.pdf#page=46]]
*Figure: the DNS namespace tree; a node stores names sharing the same suffix. (`10-IP.pdf` p. 46)*

> [!example] Where is a name stored?
>
> - `Fred.com` → under `com`
> - `Fred.edu` → under `edu`
> - `Fred.ust.hk` → under `hk` → `ust`
> - `Fred.ece.ust.hk` → under `hk` → `ust` → `ece`
> - `Fred.home.ece.ust.hk` → under the `home.ece.ust.hk` subtree

### 4.2 Zones

A **zone** is a contiguous section of the namespace — a complete tree, a single node, or a subtree. Each zone has an associated set of **authoritative name servers** that actually hold the name → IP mappings.

![[10-IP.pdf#page=48]]
*Figure: zones partition the namespace; each zone has its own name servers. (`10-IP.pdf` p. 48)*

The root sits at the top of all zones.

![[10-IP.pdf#page=49]]
*Figure: the root zone is at the top of all zones; root server A is at Verisign, Dulles, VA. (`10-IP.pdf` p. 49)*

### 4.3 Root servers and anycast

There are **13 root server identities** (A–M), replicated at many locations using **anycast**.

![[10-IP.pdf#page=50]]
*Figure: the 13 root server identities and their many locations. (`10-IP.pdf` p. 50)*

**Anycast:** multiple machines advertise the *same* IP address. Routing delivers each packet to the **closest** machine advertising that address.

![[10-IP.pdf#page=51]]
*Figure: anycast — many replicas share one address; the network picks the nearest. (`10-IP.pdf` p. 51)*

> [!example] Anycast in one sentence
>
> If the root address is advertised from Hong Kong and California, a user in Hong Kong reaches the Hong Kong replica without changing any routing algorithm.

### 4.4 The root does not know every name

The root does **not** store the IP of `potato.ece.ust.hk`. It only returns a **referral** to the name server for `.hk`. Higher-level servers mainly point to lower-level servers; only **authoritative** servers hold the final mapping.

![[10-IP.pdf#page=52]]
*Figure: the root refers queries downward; it does not store all names. (`10-IP.pdf` p. 52)*

## 5. How a lookup works

Your client usually talks to a **local resolver** — a DNS server in your network that queries on your behalf. You learn its address via **DHCP**, the same protocol that gives you your IP address and default gateway.

![[10-IP.pdf#page=61]]
*Figure: the client uses a local resolver, not the root server directly. (`10-IP.pdf` p. 61)*

The client makes a **recursive** query to the resolver: *“finish this lookup for me.”*

![[10-IP.pdf#page=62]]
*Figure: recursive query from client to local resolver. (`10-IP.pdf` p. 62)*

The resolver then performs **iterative** queries: each server it asks either answers or refers it to the next server down the tree.

![[10-IP.pdf#page=63]]
*Figure: iterative queries from the resolver: root → `.edu` → `nyu.edu`. (`10-IP.pdf` p. 63)*

> [!example] Resolving `potato.ece.ust.hk`
>
> 1. Client → local resolver: *“What is `potato.ece.ust.hk`?”* (recursive)
> 2. Resolver → root: *“Where is `.hk`?”* → root refers to the `.hk` servers.
> 3. Resolver → `.hk` servers: *“Where is `ust.hk`?”* → referral to `ust.hk`.
> 4. Resolver → `ust.hk` servers: *“Where is `ece.ust.hk`?”* → referral to ECE.
> 5. Resolver → ECE authoritative server: *“What is `potato.ece.ust.hk`?”* → returns the IP.
> 6. Resolver caches the answer for its **TTL**, then returns it to the client.
>
> Most DNS servers do **not** perform full recursive resolution all the way down; recursion is mainly between client and resolver.

### Caching

DNS servers cache responses. Each response carries a **time to live (TTL)**; after it expires, the entry is deleted.

![[10-IP.pdf#page=64]]
*Figure: caching reduces load and delay at every level. (`10-IP.pdf` p. 64)*

Caching works well because:

- top-level servers rarely change;
- popular sites are visited often;
- the local resolver often already has the answer.

![[10-IP.pdf#page=65]]
*Figure: a second client benefits from the resolver's cached answer. (`10-IP.pdf` p. 65)*

## 6. DNS resource records

The DNS database is a set of **resource records (RRs)** in the Internet (`IN`) class:

```text
(class, name, value, type, ttl)
```

| Type | Name is… | Value is… | Example |
|---|---|---|---|
| **A** | hostname | IPv4 address | `www.foobar.com → 212.44.9.130` |
| **NS** | domain | authoritative name server for that domain | `foobar.com → dns1.foobar.com` |
| **CNAME** | alias | canonical (real) name | `www → foobar.com` |
| **MX** | domain | mail server hostname | `foobar.com → mail.foobar.com` |

### Registering a domain

![[10-IP.pdf#page=60]]
*Figure: inserting records for a new company `foobar.com`. (`10-IP.pdf` p. 60)*

> [!example] New company `FooBar`
>
> 1. Get `212.44.9.128/25` from an ISP.
> 2. Register `foobar.com` with a registrar.
> 3. Registrar inserts into the `.com` TLD server:
>    - `(foobar.com, dns1.foobar.com, NS)`
>    - `(dns1.foobar.com, 212.44.9.129, A)`
> 4. You put your own records on `dns1.foobar.com`, e.g. an **A** record for `www.foobar.com` and an **MX** record for `foobar.com`.

## 7. DNS message format

A DNS message starts with a **12-byte header**:

- **Identification** — matches requests with responses.
- **Flags** — query/response, authoritative or not, recursion desired, recursion available.
- **Counts** — number of questions, answer RRs, authority RRs, additional RRs.

![[10-IP.pdf#page=67]]
*Figure: DNS message header and variable-length sections. (`10-IP.pdf` p. 67)*

The sections are:

1. **Question** — name and type being queried.
2. **Answers** — RRs answering the query.
3. **Authority** — records for authoritative servers.
4. **Additional** — helpful extra records.

![[10-IP.pdf#page=68]]
*Figure: meaning of the header flags. (`10-IP.pdf` p. 68)*

## 8. DNS as indirection

The bigger benefit of DNS is not memorability — it is **indirection** between clients and servers.

### One name → many IP addresses

![[10-IP.pdf#page=71]]
*Figure: one DNS name can map to multiple servers. (`10-IP.pdf` p. 71)*

Uses:

- **Load balancing:** half the clients get server A, half get server B.
- **Performance:** clients in Asia get the Asian server; clients in North America get the US server.
- **Migration:** move from AWS to Google Cloud by changing the DNS record, not by telling every client.

### One IP address → many names

![[10-IP.pdf#page=72]]
*Figure: many domain names can share one IP address and one port. (`10-IP.pdf` p. 72)*

A cloud provider can host many websites on one machine. Clients include the requested domain name, so the web server knows which site to serve — **multiplexing on multiplexing**.

> [!example] Virtual hosting
>
> `ust.hk` and `ece.ust.hk` can resolve to the same IP and port. The HTTP `Host` header tells the server which site the client wants.

---

## 9. Takeaways

- Internetworking needs a **common address format**; IP provides it.
- DNS is **hierarchical** in namespace, administration, and servers — not one central database.
- The root and TLD servers mostly return **referrals**; only authoritative servers hold the final answer.
- The client→resolver query is **recursive**; resolver→other servers queries are usually **iterative**.
- **Caching + TTL** is what makes DNS fast and scalable.
- DNS names are an **indirection layer**: one name → many IPs, or many names → one IP.

> [!warning] Exam traps
> - The **root server does not know** the IP of every host; it points to the next zone.
> - **A** record = IPv4 address; **NS** = name server; **CNAME** = alias; **MX** = mail server.
> - DNS is **not** centralized. It is a distributed hierarchy.
> - **Ports** identify processes; **IP addresses** identify hosts.
> - Anycast delivers to the **closest** replica advertising the address.
> - Caching is bounded by **TTL**, not permanent.
> - `dig`/`nslookup` showing a name does not mean the server is reachable — DNS and routing are separate.
