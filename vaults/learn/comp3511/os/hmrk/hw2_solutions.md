## 1. Multiple Choices [30 points]

| MC1 | MC2 | MC3 | MC4 | MC5 | MC6 | MC7 | MC8 | MC9 | MC10 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **B** | **D** | **A** | **C** | **C** | **B** | **A** | **D** | **C** | **B** |

**MC1 — B (Responsiveness).** The four benefits of multithreading are responsiveness, resource sharing, economy, and scalability. When one thread blocks (e.g., on I/O) but another thread keeps responding to the user, the application stays responsive — that is the definition of *responsiveness*.

**MC2 — D (Data parallelism).** Data parallelism = split the **data** into subsets and run the **same operation** on each subset concurrently on different cores. (Task parallelism, by contrast, gives different threads *different* operations — options A and C are task parallelism; B is just sequential.)

**MC3 — A.** Signals are classified by how they are generated: a **synchronous** signal is delivered to the same process that caused the event (e.g., division by zero, illegal memory access); an **asynchronous** signal is generated by an event **external** to the running process (e.g., timer expiration, Ctrl+C). So division by zero → synchronous, timer expiration → asynchronous.

**MC4 — C.** In **deferred cancellation**, the target thread **periodically checks** (at cancellation points) whether it has been requested to terminate, so it can clean up and exit **in an orderly manner**. Immediate termination is *asynchronous* cancellation (the alternative).

**MC5 — C.** Preemptive scheduling means the CPU is taken away **involuntarily**. Time-quantum expiry (RR timer interrupt) forces the running process back to the ready queue — that is preemption. Options A, B, D are all cases where the process **voluntarily** gives up the CPU (terminate / I/O wait / wait() call) — non-preemptive events.

**MC6 — B.** The **convoy effect** in FCFS: one long process arrives first, and many short processes pile up behind it, producing an excessively long average waiting time.

**MC7 — A.** **Aging** gradually increases the priority of a process that has been waiting a long time, guaranteeing it eventually gets the CPU — it is the standard fix for **starvation** in priority scheduling. (Predicting the next CPU burst is exponential averaging; option D describes rate-monotonic scheduling.)

**MC8 — D.** When the **thread library** decides which **user thread** runs on an available **LWP** within one process, that is **PCS (Process-Contention Scope)** — the competition is among threads of the **same process**. SCS is the kernel scheduling kernel threads among *all* threads in the system onto CPUs.

**MC9 — C (9 ms).** Exponential averaging: τₙ₊₁ = α·tₙ + (1−α)·τₙ = 0.25 × 6 + 0.75 × 10 = 1.5 + 7.5 = **9 ms**.

**MC10 — B (4 s).** Little's formula: L = λ × W ⟹ W = L / λ = 12 processes / 3 processes-per-second = **4 seconds**.

## 2. Short Answer [30 points]

### 2.1 Different PC/register values for threads of the same process?

**Yes.** Threads of the same process share the code, data (global variables, heap), and open files, but each thread has its **own execution state**: program counter, register contents, and stack. Two threads can be executing at completely different places in the code (even different functions), so their PC and register values differ. When a thread is **not running**, these values are saved in its **TCB (Thread Control Block)** — the thread-level analogue of the PCB — which stores the thread ID, PC, register set, and stack pointer.

### 2.2 Many-to-one model: parallel execution on 4 cores?

**No.** In the many-to-one model, **all user threads are multiplexed onto a single kernel thread**, and the OS only schedules kernel threads. Since the whole process presents **only one schedulable kernel thread**, the kernel can place it on **at most one core** at any instant. Moreover, the thread library switches among the user threads, and if one user thread makes a blocking system call, the single kernel thread blocks and the **entire process blocks**. So true parallelism across the four cores is impossible for this process.

### 2.3 Ctrl+C: synchronous or asynchronous? Can it be handled differently?

**Asynchronous.** The SIGINT signal is generated **outside the running process** — by the terminal driver in response to the keystroke — and is delivered at an unpredictable point in the process's execution. It is not caused by an instruction the process itself executed (contrast: division by zero → synchronous).

**Yes**, the program can override the default action (terminate). It can install a **user-defined signal handler**, e.g., with the `signal()` system call:

```c
signal(SIGINT, my_handler);   // run my_handler() instead of dying
```

A signal can be handled by (1) the **default handler**, (2) a **user-defined handler**, or (3) it can be **ignored/blocked** — the process simply declares to the kernel which it wants for each signal type.

### 2.4 Hard affinity {CPU0, CPU1}: may the OS migrate T to idle CPU2?

**No.** **Hard affinity** is a **hard constraint**: the thread has explicitly specified (via a system call) the subset of processors on which it is allowed to run, and the scheduler **must honor** that set. Since CPU2 ∉ {CPU0, CPU1}, T may only be scheduled on CPU0 or CPU1, even if that leaves CPU2 idle. Load balancing (push/pull migration) cannot override hard affinity; the OS could instead leave T queued on CPU0/CPU1 or migrate some *other* thread to CPU2. (Only *soft* affinity may be violated to balance load.)

### 2.5 RM vs EDF at t = 50 ms — same choice?

**No.** At t = 50 both A (second instance, 25 ms work, deadline 100) and B (first instance, 10 ms work remaining, deadline 80) are ready.

- **Rate-Monotonic (static priority = shorter period wins):** A's period 50 < B's period 80 ⟹ A has the higher priority ⟹ **RM chooses A**. (A then runs 50–75, B runs 75–85 and **misses its deadline of 80** — RM fails here since total utilization 25/50 + 35/80 = 0.9375 exceeds the RM bound.)
- **Earliest-Deadline-First (dynamic priority = earlier deadline wins):** B's deadline 80 < A's deadline 100 ⟹ **EDF chooses B**. (B runs 50–60 and meets its deadline; A then runs 60–85, comfortably before its deadline of 100 — EDF meets both deadlines.)

So the two algorithms make **different** choices: RM → A, EDF → B.

## 3. Calculation and Analysis [40 points]

### 3.1 Amdahl's Law

Formula: speedup ≤ 1 / (s + (1 − s)/N), where s = serial fraction, N = number of cores.

**(a) Four cores:** s = 0.2, parallel fraction = 0.8.

$$\text{speedup} = \frac{1}{0.2 + 0.8/4} = \frac{1}{0.2 + 0.2} = \frac{1}{0.4} = \mathbf{2.5\times}$$

**(b) N → ∞:** the parallel part vanishes (0.8/N → 0), so:

$$\lim_{N\to\infty} \frac{1}{0.2 + 0.8/N} = \frac{1}{0.2} = \mathbf{5\times}$$

The serial 20% caps the speedup at 5× no matter how many cores are added.

### 3.2 CPU Scheduling

Processes: P1 (arrival 0, burst 7), P2 (1, 3), P3 (4, 5), P4 (10, 2).

#### (a) SRTF — Shortest Remaining Time First

Decision trace:
- **t=0:** only P1 → run P1.
- **t=1:** P2 (3) arrives; P1 has 6 remaining > 3 ⟹ preempt → run P2.
- **t=4:** P2 finishes; P3 (5) arrives; P1 has 6 remaining > 5 ⟹ run P3.
- **t=9:** P3 finishes; only P1 (6 left; P4 not yet here) → run P1.
- **t=10:** P4 (2) arrives < P1's 5 remaining ⟹ preempt → run P4.
- **t=12:** P4 finishes → run P1 to completion.

**Gantt chart:**

```
|  P1  |   P2    |     P3      | P1 |  P4  |      P1       |
0      1         4             9   10     12              17
```

| Process | Arrival | Burst | Completion | Turnaround = C − A | Waiting = T − burst |
| --- | --- | --- | --- | --- | --- |
| P1 | 0 | 7 | 17 | 17 | 10 |
| P2 | 1 | 3 | 4 | 3 | 0 |
| P3 | 4 | 5 | 9 | 5 | 0 |
| P4 | 10 | 2 | 12 | 2 | 0 |

- **Average waiting time** = (10 + 0 + 0 + 0) / 4 = **2.5 ms**
- **Average turnaround time** = (17 + 3 + 5 + 2) / 4 = **6.75 ms**

#### (b) Round-Robin, quantum = 3 ms

Ready-queue trace (new arrivals → tail; quantum-expired process → tail):
- **t=0–3:** P1 runs (rem 4). P2 arrived at t=1. Queue: [P2], P1 rejoins → [P2, P1].
- **t=3–6:** P2 runs 3 ms, **finishes**. P3 arrived at t=4. Queue: [P1, P3].
- **t=6–9:** P1 runs (rem 1). Queue: [P3], P1 rejoins → [P3, P1].
- **t=9–12:** P3 runs (rem 2). P4 arrived at t=10. Queue: [P1, P4], P3 rejoins → [P1, P4, P3].
- **t=12–13:** P1 runs 1 ms, **finishes**. Queue: [P4, P3].
- **t=13–15:** P4 runs 2 ms (< quantum), **finishes**. Queue: [P3].
- **t=15–17:** P3 runs 2 ms, **finishes**.

**Gantt chart:**

```
|   P1    |   P2    |   P1    |   P3    | P1 |  P4   |  P3   |
0         3         6         9        12   13      15      17
```

| Process | Arrival | Burst | Completion | Turnaround = C − A | Waiting = T − burst |
| --- | --- | --- | --- | --- | --- |
| P1 | 0 | 7 | 13 | 13 | 6 |
| P2 | 1 | 3 | 6 | 5 | 2 |
| P3 | 4 | 5 | 17 | 13 | 8 |
| P4 | 10 | 2 | 15 | 5 | 3 |

- **Average waiting time** = (6 + 2 + 8 + 3) / 4 = **4.75 ms**
- **Average turnaround time** = (13 + 5 + 13 + 5) / 4 = **9 ms**

*(Note: SRTF beats RR on both averages here, as expected — SRTF is optimal w.r.t. average waiting time; RR trades that for better response time.)*

### 3.3 Multilevel Feedback Queue (MLFQ)

Rules used: Q0 = RR q=4, Q1 = RR q=8, Q2 = FCFS; new jobs → tail of Q0; full Q0 quantum → tail of Q1; full Q1 quantum → tail of Q2; a Q0 arrival preempts a running Q1/Q2 job, which returns to the **head** of its queue keeping its **remaining** quantum.

Processes: P1 (arrival 0, burst 20), P2 (1, 5), P3 (11, 2).

Simulation trace:
- **t=0:** P1 arrives → Q0. P1 runs in Q0. (P2 arrives at t=1 into Q0, but new Q0 arrivals do **not** preempt a Q0 job — RR continues.)
- **t=4:** P1 used its full 4 ms Q0 quantum (rem 16) → **tail of Q1**. Q0 = [P2] → P2 runs in Q0.
- **t=8:** P2 used its full 4 ms (rem 1) → **tail of Q1**. Q1 = [P1, P2]; Q0 empty → P1 (head of Q1) runs with an 8 ms quantum.
- **t=11:** **P3 arrives at Q0 → preempts P1 (running from Q1).** P1 has used 3 of its 8 ms quantum (rem 13 burst) → returns to **head of Q1**, ahead of P2, with **5 ms quantum remaining**. P3 runs in Q0.
- **t=13:** P3 (burst 2 ≤ 4) **finishes**. Q0 empty → P1 resumes at head of Q1 with its remaining 5 ms.
- **t=18:** P1 exhausts its Q1 quantum (3 + 5 = 8 total; burst rem 8) → **tail of Q2**. Q1 = [P2] → P2 runs; burst 1 < 8, so P2 **finishes at t=19**.
- **t=19:** Q0, Q1 empty → P1 runs in **Q2 (FCFS)** for its remaining 8 ms, **finishes at t=27**.

#### (a) Gantt chart

```
| P1(Q0) | P2(Q0) | P1(Q1) | P3(Q0) |    P1(Q1)    | P2(Q1) |      P1(Q2)      |
0        4        8       11       13             18       19                 27
```

Completion times: P1 = 27, P2 = 19, P3 = 13.

#### (b) Where does P1 go at t=11, and with how much quantum?

P1 is placed at the **head of Q1**, i.e., **ahead of P2** (which sits at the tail of Q1, having been demoted from Q0 at t=8). P1 had consumed **3 ms** of its 8 ms Q1 quantum (it ran from t=8 to t=11), so it retains **8 − 3 = 5 ms** of Q1 quantum — it does **not** receive a fresh quantum when it resumes. That is why, after P3 finishes at t=13, P1 runs only 13→18 (5 ms) before being demoted to Q2, even though it was interrupted.
