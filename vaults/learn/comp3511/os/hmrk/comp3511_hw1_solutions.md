### MC1 — I/O and DMA: **C**

The **false** statement is:

> **C)** During a DMA transfer, the DMA controller sends an interrupt to the CPU after every byte is transferred.

Why it's wrong: a DMA controller moves a **whole block** of data without CPU
involvement, and it interrupts the CPU **once**, when the whole transfer is done —
not after every byte. (Interrupting per byte would be "programmed I/O" behavior,
which DMA is designed to avoid.)

- A is true: programmed I/O = CPU runs special I/O instructions to move data.
- B is true: DMA transfers a block without continuous CPU involvement.
- D is true: DMA sends an interrupt to signal completion of the block.

### MC2 — Interrupts and traps: **B**

The **false** statement is:

> **B)** Interrupts can only be generated by I/O devices.

Why it's wrong: interrupts come from more than just I/O devices. They can also come
from **hardware faults** (e.g., the clock/timer), and **traps/exceptions** are
software-generated interrupts (e.g., a system call or a divide-by-zero).

- A is true: hardware interrupts are asynchronous w.r.t. the current instruction.
- C is true: a trap is caused by an error or a user request (system call).
- D is true: interrupts have priority levels (a high-priority interrupt can preempt a low-priority one).

### MC3 — Resource allocator: **C**

Deciding which job gets CPU time and how memory is allocated is exactly the OS role
of a **resource allocator**.

### MC4 — SMP / multicore / NUMA: **D**

The **false** statement is:

> **D)** In NUMA, every CPU accesses every part of memory with exactly the same latency.

Why it's wrong: NUMA = **Non-Uniform Memory Access**. A CPU accesses *its local*
memory faster than *remote* memory (that's the whole point of "non-uniform").
Equal latency for all memory is the property of **UMA/SMP**, not NUMA.

- A, B, C are all true statements.

### MC5 — OS structures: **B**

> **B)** A microkernel keeps only essential functions in the kernel and provides other
> services outside the kernel through communication mechanisms such as message passing.

This is the definition of a microkernel.

- A is false: moving most services to user space is the **microkernel** approach, not monolithic.
- C is false: in a layered OS each layer can only call the layers *directly below* it.
- D is false: loadable kernel modules are linked **dynamically** — no full recompile/reboot required.

### MC6 — How `read()` reaches the OS: **C**

> **C)** The API and run-time environment use the system-call interface to invoke the
> corresponding kernel service, and control later returns to the application.

The user program calls the `read()` **API** (library), the run-time environment goes
through the **system-call interface** into the kernel, and control returns afterwards.
(A is wrong — user mode can't execute privileged I/O instructions; B is wrong — the
kernel does the work; D is wrong — no new process is created per `read()`.)

### MC7 — Privileged instruction in user mode: **A**

> **A)** The hardware treats the instruction as illegal and traps to the operating system.

A privileged instruction executed in user mode is treated as illegal and causes a
**trap** into the OS (this is the dual-mode protection mechanism). The user program
cannot change the mode bit by itself, and the instruction is not silently discarded.

### MC8 — Virtualization: **B**

The **false** statement is:

> **B)** An application always runs faster inside a virtual machine than directly on the physical machine.

Virtualization adds overhead (VMM, machine switches, emulation), so apps typically
run **slower** — not faster — inside a VM. A, C, D are all correct statements.

### MC9 — `fork()`: **C**

The **false** statement is:

> **C)** If the child changes a global variable after `fork()`, the parent's copy of that variable changes automatically.

After `fork()`, parent and child have **separate copies** of the address space.
Modifying a variable in one process does **not** affect the other. A, B, D are all true.

### MC10 — Pipes: **D**

The **false** statement is:

> **D)** A named pipe ceases to exist as soon as the communicating processes terminate.

Named pipes (FIFOs) **persist** in the file system until explicitly deleted — they
don't vanish when the processes exit. (That behavior describes an *ordinary/anonymous*
pipe, not a named pipe.) A, B, C are true.

## Section 2 — Short Answer

### 1) Cache average access time + locality (6 pts)

**Average access time:**

```
T_avg = (hit ratio × hit time) + (miss ratio × miss time)
      = (0.90 × 2 ns) + (0.10 × 50 ns)
      = 1.8 ns + 5.0 ns
      = 6.8 ns
```

**Temporal locality:** if a memory location is accessed, it is *likely to be accessed
again soon*.

- Example: a **loop counter** or a variable used repeatedly inside a loop is accessed
  again and again in a short period.

**Spatial locality:** if a memory location is accessed, *nearby* locations are likely
to be accessed soon.

- Example: iterating through an **array** accesses consecutive elements, and
  **sequential instruction fetch** reads instructions one after another in memory.

### 2) Multiprogramming and time sharing (6 pts)

**How multiprogramming improves CPU utilization:** it keeps **several jobs in memory
at once**, so that whenever the currently running process **blocks** (e.g., waiting for
slow I/O), the OS can immediately switch the CPU to another ready process instead of
letting the CPU sit idle. This overlaps one job's I/O with another job's computation,
keeping the CPU busy and maximizing utilization.

**What time sharing / multitasking adds:** it adds **rapid, timer-driven switching**
between processes (frequent context switches / preemption) so that multiple interactive
users each get a small slice of CPU time. This makes the system **responsive** and gives
each user the *illusion* of having the machine to themselves — the key requirement for
interactive computing.

### 3) Process states + PCB contents (6 pts)

**Complete state sequence** (admitted → … → exits):

```
New → Ready → Running → Waiting → Ready → Running → Ready → Running → Terminated
```

Mapping to the described events:

| Event in the question | State entered |
|---|---|
| admitted to the system | **New** (then **Ready** to wait for CPU) |
| dispatched to a CPU | **Running** |
| requests disk I/O | **Waiting** (blocked for the I/O event) |
| resumes after I/O completes | **Ready** (back in the ready queue) |
| dispatched again | **Running** |
| preempted by a timer interrupt | **Ready** (put back in ready queue) |
| dispatched again | **Running** |
| exits | **Terminated** |

**What the OS records in the PCB when the process leaves the Running state:** it **saves
the process's execution context** so it can be resumed later exactly where it left off —
specifically:

- the **program counter** (address of the next instruction to fetch),
- the **CPU registers** (general-purpose registers, stack pointer, condition codes),
- and it updates the **process state** field (e.g., Running → Ready or Running → Waiting).

(This saved context is what a later **context switch** restores.)

### 4) `read()`: user mode → kernel mode → back (6 pts)

Three main steps:

1. **Trap into the kernel.** The user program calls the `read()` library/API function.
   The run-time environment places the system-call **number** and the **parameters**
   (file descriptor, buffer, count) in registers (or in a memory block / on the stack),
   then executes a special **trap/system-call instruction** (e.g., `syscall` / `int 0x80`).
   This changes the mode bit from **user mode → kernel mode**.

2. **Kernel handles the request.** The kernel uses the system-call number to index its
   **system-call table** and dispatches to the `read()` service routine. In kernel mode it
   performs the actual I/O (e.g., copying data from the file/device into the user's
   buffer). If data isn't ready, the process may be moved to a **wait queue** and block.

3. **Return to user mode.** When the system call finishes, the kernel returns to the
   user program; the mode bit is switched back to **user mode**, and execution resumes at
   the instruction **after** the system call, with the return value/status delivered to
   the caller.

### 5) Parent → child communication via an ordinary pipe (6 pts)

Required steps (order matters):

1. **Parent calls `pipe(fd)` *before* `fork()`.** This creates the pipe and gives
   `fd[0]` (read end) and `fd[1]` (write end).
2. **Parent calls `fork()`.** The child **inherits** both pipe file descriptors.
3. **Parent closes the read end `fd[0]`** and keeps the write end `fd[1]`; it then
   **writes** the data to `fd[1]`.
4. **Child closes the write end `fd[1]`** and keeps the read end `fd[0]`; it then
   **reads** the data from `fd[0]`.

- Direction: the pipe is **unidirectional** — here data flows **parent → child**.
- Parent calls `pipe()` **before** `fork()` (so both processes share the *same* pipe).
- Parent calls `fork()` after the pipe exists so the child inherits the descriptors.
- Each process closes the end it doesn't use (parent: read end; child: write end) and
  uses the other end (parent: write; child: read).
- After finishing, each process closes its remaining end; the parent may `wait()` for
  the child.

## Section 3 — C Programs on `fork()`

### 3.1) The `x` / two-forks program (15 pts)

```c
int main() {
     int x = 1;

     pid_t c1 = fork();
     if (c1 == 0) {
           x += 2;
           printf("C1: %d\n", x);   // C1 prints 3
           return 0;
     }

     x *= 2;                          // parent: x = 2
     pid_t c2 = fork();
     if (c2 == 0) {
           x += 3;
           printf("C2: %d\n", x);   // C2 prints 5
           return 0;
     }

     wait(NULL);
     wait(NULL);
     printf("P: %d\n", x);           // parent prints 2
     return 0;
}
```

#### (a) Values printed (6 pts)

- **C1 prints `3`** — the child gets a copy of `x = 1`, then `x += 2` → `3`.
- **C2 prints `5`** — C2 is forked *after* the parent does `x *= 2`, so it inherits
  `x = 2`, then `x += 3` → `5`.
- **P prints `2`** — the parent's own `x` became `2` after `x *= 2` and is never changed
  again (the children modify their *own copies*).

**Why the three processes have different values:** `fork()` gives the child a **separate
copy** of the parent's address space. After the fork, `x` in each process is an
independent variable — changes made in one process do **not** affect the others.

#### (b) Every possible complete output sequence (4 pts)

There are **two** possible sequences:

1. `C1: 3` → `C2: 5` → `P: 2`
2. `C2: 5` → `C1: 3` → `P: 2`

Reason: `P: 2` is always **last** because the parent calls `wait(NULL)` twice before
printing. `C1` and `C2` are independent children, so their relative order is
nondeterministic (whichever gets scheduled first prints first). Each `printf` is a
single flushed line, so the lines don't interleave.

#### (c) Moving the first `wait(NULL)` before `x *= 2` (5 pts)

```c
     pid_t c1 = fork();
     if (c1 == 0) { x += 2; printf("C1: %d\n", x); return 0; }
     wait(NULL);          // ← moved here
     x *= 2;
     pid_t c2 = fork();
     ...
```

- **Guaranteed output order:** `C1: 3` → `C2: 5` → `P: 2`. The parent now blocks until
  **C1 finishes** before it even creates C2, so C1 must print before C2 exists, and P is
  still last (parent waits for C2 at the end).
- **Do any printed values change?** **No.** C1 still prints 3; the parent still performs
  `x *= 2` (so its `x = 2`) before forking C2, so C2 still inherits 2 and prints 5; the
  parent still prints 2. Only the *order* becomes deterministic.

### 3.2) The `execlp("./worker")` program (15 pts)

```c
int main() {
     printf("A\n");

     pid_t p = fork();

     if (p == 0) {
          pid_t q = fork();

          if (q == 0) {
               execlp("./worker", "worker", (char *) NULL);
               printf("X\n");       // never reached (execlp succeeds)
               return 1;
          }

          wait(NULL);
          printf("C\n");
          return 0;
     }

     printf("P\n");
     wait(NULL);
     printf("D\n");
     return 0;
}
```

#### (a) Number of processes + tree (5 pts)

**3 processes** are involved:

```
main process (original)
├── child  (p == 0, "middle" process)
│      └── grandchild  (q == 0)  → runs ./worker (prints W)
```

The **grandchild** (`q == 0`) is the process that executes `worker` (via `execlp`), so
it prints `W`.

#### (b) Is `X` printed? (4 pts)

**No.** Because the problem states `execlp()` **succeeds**, it **replaces the current
process image** with `./worker`. Control never returns to the code after `execlp()`, so
`printf("X")` and `return 1` are never executed. (`execlp` returns only on **failure**.)

#### (c) All possible complete output sequences (6 pts)

Partial order constraints:

- `A` is always first (printed before the first fork).
- `W` before `C` (the middle process `wait`s for the grandchild before printing `C`).
- `C` before `D` (the original parent `wait`s for the middle process before printing `D`).
- `P` before `D` (the parent prints `P` before its `wait(NULL)`).

So the only remaining freedom is where `P` falls relative to `W` and `C`:

1. `A` `P` `W` `C` `D`
2. `A` `W` `P` `C` `D`
3. `A` `W` `C` `P` `D`

(There are exactly **3** possible sequences. `A` is fixed first, `D` is fixed last, and
`W → C` order is fixed; `P` can be printed before `W`, between `W` and `C`, or after
`C` but still before `D`.)

### 3.3) The pipe program (10 pts)

```c
int main() {
     int fd[2];
     pipe(fd);

     pid_t pid = fork();
     if (pid == 0) {
           int n;
           close(fd[1]);                 // child: close WRITE end
           read(fd[0], &n, sizeof(n));   // child: READ from read end
           printf("Child: %d\n", n * 2);
           close(fd[0]);
           return 0;
     }

     int n = 6;
     close(fd[0]);                       // parent: close READ end
     write(fd[1], &n, sizeof(n));        // parent: WRITE to write end
     close(fd[1]);
     wait(NULL);
     printf("Parent: done\n");
     return 0;
}
```

#### (a) Which ends are closed/used + direction (4 pts)

- **Parent:** closes the **read end** `fd[0]`, uses the **write end** `fd[1]` to send data.
- **Child:** closes the **write end** `fd[1]`, uses the **read end** `fd[0]` to receive data.

Direction of transfer: **parent → child** (parent is the producer/writer, child is the
consumer/reader).

#### (b) Exact output and why the order is guaranteed (3 pts)fd

```
Child: 12
Parent: done
```

- The child reads `n = 6` and prints `6 * 2 = 12`.
- The order is guaranteed because the parent calls `wait(NULL)` **before** printing
  `Parent: done`; the parent therefore blocks until the child exits, and the child prints
  `Child: 12` before it exits. So `Child: 12` always appears before `Parent: done`.

#### (c) Separate `pipe(fd)` calls after `fork()` (3 pts)

**No — the two pipes could not be used for the same communication.**

After `fork()`, the parent and child have **separate address spaces**. If each process
calls `pipe(fd)` independently *after* the fork, each one creates its **own, unrelated
pipe** (its own pair of kernel pipe objects). Data written to the parent's write end
would never be visible at the child's read end, because they refer to different pipes.
To share a pipe, `pipe()` must be called **once, before `fork()`**, so the child
**inherits** the same pipe's file descriptors.
